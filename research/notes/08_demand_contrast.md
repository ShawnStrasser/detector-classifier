# 08_demand_contrast — does detector behaviour that *changes with demand* add anything? (2026-09-21)

Outside idea: occupancy + green/red state compared **across off-peak and peak** classifies detectors well (needs ~a day of data). We already use exact ON/OFF intervals by colour but pooled over the window. Here each window is cut into demand periods and the model is given the low/high values, their difference, log-ratio and evidence-weighted slope, **shrunk** toward the pooled value (k in denominator units) so sparse periods collapse to 0 rather than add noise. 15 base quantities (ON median/q90, occupancy fraction, occupancy in red vs green, queue occupancy before green, release straddle, discharge burst, long/short-ON share, red-last-10 s share, call-43 linkage, actuation rate) x {lo, hi, diff, log-ratio, slope} + evidence context. Periods: **(b) data-driven** — the signal's 15-min bins ranked by total actuations, terciles (`cq_`, hi/lo demand 15x) and **(a) clock** 00-05/19-23 low, 10-14 mid, 06:30-09/15:30-18:30 high (`cc_`, 4.7x). Built only for windows >= 24 h (`h24_a, h24_b, full72`); 373 DEV signals, same 6 grouped folds, OOF, TEST untouched, base features rebuilt from cache only. Code `src/contrast/{build_contrast,contrast_features,eval_contrast,describe_contrast}.py`, artefacts `dc_work/contrast/`.

The decoder headline looked shippable (+0.23 pt, 22 % fewer concurrent-pair errors) until the control: **82 columns of the same numbers randomly permuted across detectors buy +0.16 pt of it.** Any perturbation of the first stage reshuffles which detectors the second stage rescues, so the decoder's own run-to-run noise is ~±0.2 pt — the size of the decision threshold. Only the ranker's +0.12 pt survives its control, and that is under the bar. Still notable: `cq_call43_lo`, the detector→phase-call linkage measured **off-peak only**, is the 8th most important feature of the whole phase model — at 3 am a call following an actuation within 0.35 s can only be that detector's.

## 3. Binned vs exact-interval occupancy (task 4): **no — exact is better**
Identical 405-feature sets, only the spelling of "occupancy in green / in red" changes (Delta vs exact): **exact interval .8208** | 15 s binned .8207 (−0.01 pt) | per-cycle clipped, atspm-style .8202 (−0.06) | clipped time-weighted .8185 (−0.23, CI excludes 0). On the broader 6-quantity set binned is **−0.29 pt (−0.51, −0.07), 5/6 folds worse**. Descriptively the gap is wide: between/within-class variance (A/P/C/YR) for the occupancy-in-red difference is **381 exact vs 67 binned**, for its log-ratio 203 vs 8, for queue occupancy 373 vs 83 — quantising to 15 s destroys the 0.2-2 s detail that separates Count from Presence. (`atspm`'s split-failure query is in fact not quantised: it sums exact ON milliseconds inside green and the first 5 s of red per cycle, then averages into 15-min bins. That per-cycle macro average is the row above and is also no better than our pooled micro average.)

## 4. What the contrast actually sees (medians at 72 h, low → high demand tercile)
Every hypothesis is confirmed *descriptively*. **Presence**: occupancy of red .033 → **.380**, ON q90 16.6 s → 40.9 s — the only class already occupied in red off-peak. **Advance**: occupancy of red .006 → .074, the only class whose *median* ON lengthens with demand (0.85 → 1.00 s; log-ratio .11 vs .00 for Count), mean occupancy just before green 1.0 → 1.9 s — the queue reaching back to the setback loop, exactly as predicted. **Count / Yellow_Red**: invariant — median ON 0.2 s at both ends, occupancy of red .000-.002, and Yellow_Red never straddles a begin-green (.000, vs Presence .372 → .182). **Other / "advance presence"** sits between Advance and Presence on every contrast (occ-red high .102). Surprise: Advance's call-43 linkage *falls* with demand (.87 → .49) — in the peak the phase is already called by someone else. Why it still does not pay: a 24 h pooled average is itself demand-weighted, i.e. mostly peak, and `dur_mean_red`, `dur_q90_over_med`, `queue_occ_pre_green`, `det_frac_long__sibmin` (ranks 1, 5, 6, 4) already carry it; the low-demand value is near zero for every class but Presence, so the contrast is close to a monotone transform of what the model had.

## 5. Recommendation — **do not ship an "extended" >= 24 h model**
Nothing clears the bar: function +0.28 pt at best (CI lower bound exactly 0.00) against 0.5 pt required; phase +0.23 pt of which 0.16 pt is reproduced by shuffled noise, against 0.2 pt required. A separate long-window model would also start behind — trained on >= 24 h windows only it reaches .9680 at 72 h vs the shipped 22-window model's .9707. So **no OOF contract files were written to `dc_work/preds/`**; the by-window OOF of the tested variants stays in `dc_work/contrast/`. If revisited, the route is to add the ~37 occupancy+duration contrast columns to the existing **mixed-duration** model as NaN below 24 h (one model, no mode switch, `predict.py` keeps its single path); `predict.py` would then need a 15-min actuation-count histogram per signal, a tercile cut, and the level-wise aggregation of `build_contrast.py` — ~40 lines of DuckDB, no new event codes, no change to the model contract. Fold 0 (the 2025 hold-out, a check not a target) agreed: function +0.34 pt, phase decoded +0.07 pt with its shuffled control also at +0.07 pt.

**Versus the rule-based approach (fair note).** The rules and this feature family measure the same physics, and our numbers say the physics is real: at 72 h a Presence loop's red occupancy is 5x an Advance loop's even off-peak and reaches .38 in the peak, while Count and Yellow_Red never move at all. Rules built on that need no labels, no training set and no GPU and transfer to any agency — a real advantage where we have none of the 375 labelled signals to learn from. What they need instead is ~a full day spanning both regimes. Our model does not: it reaches .804 five-class (.852 on A/P/C) function accuracy and .952 phase accuracy from **30 minutes** at any time of day, because it reads the *shape* of each actuation — median and q90 ON length, time since begin green, cross-detector lag, call linkage — instead of differencing two demand regimes. The honest comparison is therefore not better/worse but a different budget: rules buy interpretability and zero setup at the price of a 24 h sample; the learned model buys 30-minute operation and cross-detector structure at the price of labelled training data. What this stage shows is that once the learned model exists, the peak-vs-off-peak contrast the rules rely on is already inside it.

**Negatives / limits.** The whole family is 0.1-0.3 pt everywhere, i.e. indistinguishable from the fitting noise of a 6-fold LightGBM run; the shuffled-column control was the only thing that made that legible and should be standard for any future family of this size. The sibling-lag features got no contrast version (a per-level cross-correlogram is expensive); per-cycle occupancy was tested only in its atspm macro-average form; and the mixed-duration ship test in §5 was not run once the control removed the reason to. Build cost: 294 s of DuckDB (6 threads / 6 GB) for 832 k raw counter rows, 10 s to assemble 232 feature columns, ~8 min per model comparison at `n_jobs=6`.
